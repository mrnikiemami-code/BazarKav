# سند معماری بازارکاو

تاریخ: ۱۴۰۵/۰۷/۲۱ — 2026-10-13
وضعیت: تصمیم‌های گفتگو ثبت شده؛ مرز نهایی ماژول‌ها نیازمند ادامه طراحی دامین است.

## ۱. هدف و محدوده

بازارکاو داده‌های حسابداری را برای تحلیل و پیشنهاد قابل توضیح دریافت می‌کند. سیستم فقط تحلیل می‌کند؛ ثبت فاکتور، سفارش خرید، دریافت وجه یا تغییر موجودی در حسابداری در محدوده نیست.

روش اتصال پشت آداپتر قرار می‌گیرد: API، اکسل، دیتابیس مستقیم یا روش دیگر. انتخاب و پیاده‌سازی روش اتصال فعلاً به تعویق افتاده است. دسترسی آداپتر به منبع باید فقط خواندنی باشد.

## ۲. تصمیم‌های دامین

| مفهوم | مسئولیت و قاعده |
|---|---|
| کسب‌وکار | مالک داده و محدوده استقلال اطلاعات |
| Tenant | فضای مستقل یک کسب‌وکار؛ هر کسب‌وکار یک Tenant و هر کاربر می‌تواند به چند Tenant دسترسی داشته باشد |
| شعبه | بخش یک کسب‌وکار؛ گزارش مستقل و تجمیعی |
| انبار | محل نگهداری کالا؛ هر شعبه می‌تواند چند انبار داشته باشد |
| منبع حسابداری | منبع داده؛ برابر با شعبه فرض نمی‌شود |
| کالا | هویت مستقل در کسب‌وکار، گروه‌بندی و واحد اندازه‌گیری |
| مشتری | هویت مستقل در کسب‌وکار؛ می‌تواند از چند شعبه خرید کند |
| تطبیق هویت | ارتباط شناسه‌های منابع با کالا، مشتری و انبار |
| فروش | واقعیت فروش و اقلام، تاریخ، تعداد، مبلغ و مرجوعی |
| موجودی و گردش | موجودی در زمان مشخص، ورود، خروج، انتقال و اصلاح |
| داده خرید و تأمین | سابقه خرید، تأمین‌کننده و سفارش باز برای تحلیل |
| یافته تحلیلی | نتیجه همراه دلیل، دامنه، بازه زمانی و وضعیت داده |
| پیشنهاد | اقدام پیشنهادی همراه مبنای محاسبه؛ بدون اجرای عملیات |

قواعد قطعی:

1. اطلاعات کسب‌وکارهای مستقل جدا می‌ماند؛ تجمیع چند کسب‌وکار فعلاً تعریف نشده است.
2. کد کالا و مشتری در منابع مختلف می‌تواند متفاوت باشد. یکسان بودن نام یا کد، اثبات هویت مشترک نیست.
3. تطبیق قابل اصلاح است و شناسه و منشأ اصلی داده حفظ می‌شود. اصلاح تطبیق باید در تحلیل‌های بعدی منعکس شود.
4. رکوردهای تطبیق‌نیافته جدا و آشکار گزارش می‌شوند؛ تجمیع آن‌ها بدون تعیین هویت ممنوع است.
5. موجودی به ترکیب کالا و انبار و زمان وابسته است. واحدهای متفاوت بدون تبدیل معتبر جمع نمی‌شوند.
6. انتقال بین انبارها فروش نیست. مرجوعی و ابطال باید در تعریف فروش خالص لحاظ شوند.
7. کندفروش، تندفروش، راکد و مشتری دیرکرده، نتیجه تحلیل هستند؛ موجودیت پایه مستقل نیستند.
8. تحلیل هم طبق سابقه و روال واقعی و هم طبق قواعد مدیر پشتیبانی می‌شود. مبنای هر نتیجه مشخص است. اولویت یا ترکیب دو روش هنوز تصمیم‌گیری نشده است.
9. نبود داده معادل صفر یا نبود فروش نیست. گزارش باید کامل بودن پوشش زمانی و تازگی داده را نشان دهد.
10. دریافت مجدد یک سند نباید فروش یا موجودی را دوباره بشمارد. سند مشابه از دو منبع نیز بدون قاعده تعیین منشأ معتبر تجمیع نمی‌شود.

## ۳. حوزه‌های پیشنهادی

| حوزه | مسئولیت |
|---|---|
| ساختار کسب‌وکار | کسب‌وکار، شعبه و انبار |
| کالاها | هویت کالا، گروه و واحدها |
| مشتریان | هویت مشتری در کسب‌وکار |
| تطبیق هویت‌ها | ارتباط هویت داخلی و شناسه منابع |
| تحلیل فروش | سرعت، روند، سود، تخفیف و مرجوعی |
| تحلیل مشتریان | الگوی خرید، دیرکرد، افت فعالیت و ارزش مشتری |
| تحلیل موجودی و تأمین | رکود، مازاد، اتمام، تأمین و انتقال پیشنهادی |
| قواعد تحلیل | تنظیمات مدیر و معیارهای مبتنی بر روال |

این حوزه‌ها فهرست اولیه دامین هستند؛ هر سطر الزاماً یک ماژول مستقل نیست. هیچ ماژولی صرفاً برای پرکردن فولدرها ساخته نمی‌شود. قواعد تخصصی هر تحلیل متعلق به همان حوزه است؛ حوزه قواعد تحلیل نباید به محل انباشت تمام منطق تحلیل تبدیل شود.

گزارش‌های سود، بدهی، زمان تأمین و فروش ازدست‌رفته به داده لازم وابسته‌اند. مقدار برآوردی باید از مقدار مشاهده‌شده متمایز باشد.

## ۴. سبک معماری و وابستگی‌ها

مبنا: بک‌اند C#/.NET 10، یک برنامه ماژولار با معماری تمیز در هر ماژول. نسخه‌های پایه در ADR-001 ثبت شده‌اند. PostgreSQL و EF Core برای Tenant در ADR-002 انتخاب شدند؛ فناوری WebApp هنوز انتخاب نشده است.

- Domain: مدل، قواعد و سیاست‌های کسب‌وکار؛ مستقل از MediatR، EF، HTTP، لاگ و آداپتر.
- Application: کاربردها، هماهنگی اجرا، قراردادهای موردنیاز و handlerهای MediatR.
- Infrastructure: پیاده‌سازی قراردادهای Application، ذخیره‌سازی و آداپترها.
- Presentation: endpoint، نگاشت ورودی و پاسخ و ارسال درخواست به MediatR.
- Contracts: قراردادهای عمومی یک ماژول؛ DTO و قرارداد تعامل، بدون Entity، DbContext یا منطق داخلی.
- Host: composition root؛ ثبت وابستگی‌ها، تنظیم pipeline و راه‌اندازی. هیچ منطق تحلیل یا endpoint اختصاصی ماژول در Host قرار نمی‌گیرد.

Domain هیچ ProjectReference یا PackageReference ندارد.
Application فقط به Domain و Contracts خودش، Contracts ماژول‌های دیگر و BuildingBlocks/Application وابسته می‌شود.
Infrastructure به لایه‌های داخلی خودش، Contracts سایر ماژول‌ها و BuildingBlocks/Application یا Observability وابسته می‌شود.
Presentation فقط به Application و Contracts خودش، Contracts سایر ماژول‌ها و BuildingBlocks/Web یا Application وابسته می‌شود.
Host به Infrastructure و Presentation ماژول‌ها و BuildingBlocks/Web و Observability برای ترکیب اجزا وابسته می‌شود.
ارتباط بین ماژول‌ها فقط از Contracts می‌گذرد؛ ارجاع به Domain، Application یا Infrastructure ماژول دیگر ممنوع است.

هر لایه یک پروژه مستقل خواهد بود تا وابستگی‌ها قابل بررسی باشند. Contracts نیز پروژه مستقل است. وابستگی دوری ممنوع است.

## ۶. MediatR، Command، Query و Validation

- endpoint فقط درخواست را به ISender ارسال می‌کند؛ دسترسی مستقیم به DbContext، Repository یا آداپتر ندارد.
- Command تغییر وضعیت داخلی برنامه، مانند تنظیم قاعده، تطبیق یا شروع کار تحلیل را بیان می‌کند؛ مجوز تغییر حسابداری بیرونی نیست.
- Query فقط می‌خواند؛ تغییر وضعیت کسب‌وکار یا شروع پنهانی همگام‌سازی ممنوع است.
- handlerهای Command در Commands و handlerهای Query در Queries قرار می‌گیرند.
- تمام FluentValidation validatorها فقط در Application/Validation قرار می‌گیرند.
- ValidationBehavior قبل از handler اجرا می‌شود؛ قواعد دامنه همچنان در Domain محافظت می‌شوند.
- pipeline پایه: LoggingBehavior بیرونی، سپس ValidationBehavior و handler. tracing از همان Activity درخواست استفاده می‌کند.
- هیچ behavior عمومی به‌صورت خودکار retry یا transaction را روی تمام درخواست‌ها اعمال نمی‌کند.
- CancellationToken تا لایه داده و آداپتر منتقل می‌شود. cancellation نباید به موفقیت، داده خالی یا خطای ۵۰۰ تبدیل شود.
- نسخه و مجوز MediatR و FluentValidation هنگام انتخاب بسته‌ها بررسی و دقیقاً pin می‌شوند؛ ارتقای خودکار ممنوع است.

## ۷. لاگ، Correlation و Trace

- لاگ ساختاریافته با message template؛ زیرساخت پیشنهادی Serilog و OpenTelemetry در زمان پیاده‌سازی بررسی می‌شود.
- TraceId و SpanId از Activity و W3C trace context؛ CorrelationId شناسه مستقل قابل ارائه به کاربر است.
- CorrelationMiddleware مقدار ورودی X-Correlation-ID را از نظر طول و کاراکتر معتبر می‌کند؛ مقدار نامعتبر با شناسه تازه جایگزین می‌شود.
- شناسه در response header و ProblemDetails و scope لاگ قرار می‌گیرد. CorrelationId هویت امنیتی یا مبنای تشخیص کسب‌وکار نیست.
- scope استاندارد: CorrelationId، TraceId، SpanId، BusinessId معتبر، BranchId در صورت وجود، SourceId، Module، Operation و DurationMs.
- دریافت پس‌زمینه یک Activity مستقل دارد و شناسه کار و ارتباط آن با درخواست آغازکننده را نگه می‌دارد.
- خطای غیرمنتظره یک بار در مرز مالک اجرا با exception کامل ثبت می‌شود؛ behavior و middleware آن را دوباره ثبت نمی‌کنند.
- رمز، توکن، connection string، محتوای کامل فایل‌ها، شماره تماس و payload حسابداری در لاگ عمومی ثبت نمی‌شوند.
- مقصد، retention و دسترسی لاگ قابل تنظیم است؛ نسخه اول به سرویس ابری وابسته نمی‌شود.

## ۸. خطاهای حرفه‌ای

Domain خطاهای معنی‌دار با کد پایدار دارد؛ HTTP status در Domain قرار نمی‌گیرد. خطاهای موردانتظار با نتیجه نوع‌دار و خطاهای غیرمنتظره با exception مدیریت می‌شوند. پیاده‌سازی دقیق Result هنگام ایجاد پایه انتخاب می‌شود.

نگاشت مرکزی در BuildingBlocks/Web/Errors به ProblemDetails:
- ورودی یا validation نامعتبر: 400، با خطاهای فیلدی.
- دسترسی نامعتبر: 401 یا 403؛ نبود داده قابل دسترسی: 404.
- تعارض وضعیت داخلی: 409.
- عدم دسترسی موقت به منبع بیرونی در عملیات همزمان: 503؛ timeout upstream: 504.
- خطای غیرمنتظره: 500 با پیام عمومی.

extensions شامل code، correlationId و traceId است. stack trace، SQL، exception خام و اطلاعات اتصال به پاسخ کاربر وارد نمی‌شوند. پاسخ و پیام نمایشی فارسی است؛ کدها پایدار و مستقل از زبان‌اند.
نبود قابلیت در منبع، داده ناقص و خطای اتصال سه وضعیت جدا هستند؛ هیچ‌کدام گزارش صفر و موفق تولید نمی‌کنند.

## ۹. جداسازی و کیفیت داده

BusinessId از زمینه معتبر دسترسی تعیین می‌شود؛ header یا DTO دلخواه کاربر به‌تنهایی قابل اعتماد نیست. همه خواندن‌ها و گزارش‌ها محدوده کسب‌وکار را اعمال می‌کنند. تفکیک شعبه و انبار داخل همان کسب‌وکار بررسی می‌شود.

منشأ داده، شناسه اصلی، زمان رویداد، زمان دریافت و بازه پوشش حفظ می‌شوند. آداپتر داده را به مدل ورودی تبدیل می‌کند؛ تعریف تندفروش یا راکد در آداپتر ممنوع است. مدل خام منبع وارد Domain تحلیل نمی‌شود.

هر یافته شامل دامنه کسب‌وکار/شعبه/انبار، بازه بررسی، مبنای قاعده و نسخه آن، شواهد، زمان تحلیل و تازگی داده است. تغییر قواعد مدیر یا تطبیق هویت‌ها نباید معنای یک نتیجه قبلی را بی‌صدا عوض کند.

## ۱۰. کنترل معماری و تصمیم‌های باز

گاردهای اجرایی فعلی: مسیر فایل‌ها، جداسازی Command/Query/Validation، ارجاع پروژه‌ها، پاکی Domain و Contracts و چرخه وابستگی.
کنترل‌های معنایی مانند دسترسی مستقیم endpoint به داده، isolation، خواندنی بودن آداپتر و نشت اطلاعات باید هنگام پیاده‌سازی با ArchitectureTests و integration tests تکمیل شوند؛ گارد فعلی اثبات آن‌ها نیست.

ماژول اول Tenant و مرز آن قطعی است؛ ADR-002 مسئولیت و دسترسی registry مدیریتی را تعیین می‌کند.
هنوز باز: مرز سایر ماژول‌ها، frontend، رابطه دقیق منابع با شعب، اولویت قواعد مدیر و روال، تعریف شاخص‌ها، provider احراز هویت، عضویت و مجوز کاربران، دریافت داده و رفع همپوشانی منابع.
